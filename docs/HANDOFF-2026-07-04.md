## PART B — BACKEND (`not_for_all`, codename Hellcat)

### Two repos — audit the RIGHT one
- **`mizerovkuzma/not_for_all`** = partner's upstream. **Last push 2026-07-04 (today, ~17:50 UTC)** — this is the live, current code. Readable with founder's `gh`.
- **`convyrtech/not_for_all`** = founder's FORK, last push **2026-05-10 (STALE)**. Do NOT audit against this — it's ~2 months behind prod.
- Stack (from repo): FastAPI app (`/opt/hellcat-app`), Marzneshin `dawsh/marzneshin` v0.7.4, aiogram bot, chain bridge→exit; ops in `ops/` (systemd timers: backup, e2e-probe, heartbeat, watchdogs), runbooks in `docs/RECOVERY_RUNBOOK.md` + `docs/HELLCAT_OPS.md`.

### Access reality
- Founder has **repo access to both** (fork + partner upstream readable).
- Founder does **NOT have server access** — the partner controls the box and it is not shared.

### CRITICAL blockers (in priority order)
1. **Hosting unpaid → server DOWN → key issuance DEAD.** The site's issuance proxy `POST /external/issue-key` (HMAC-signed) runs on the partner's box. Confirmed this session: the admin "Выдать ключ" button hangs ~21s then fails, and auto-issue after payment fails — because the box doesn't answer (the proxy URL is set in Vercel env, but nothing responds; TLS to the subscription host `cloudasset-dl.com` also tarpits). Root cause per founder: partner forgot to pay the hosting bill. **This is recoverable IF fast** — pay the bill before the provider wipes the disk.
2. **NO off-site backup → prod data is hostage.** `docs/RECOVERY_RUNBOOK.md` §0: "Remote backup copy … rsync to Nebius S3 is **pending**"; `offsite_sync.sh` is disabled. So the ONLY copies of the app PostgreSQL DB, the Marzneshin sqlite (user↔key mappings), subscription tokens, and `configs-*.tgz` live on that one box. If the provider wipes it before the bill is paid, the data is gone → forced fresh rebuild → every existing user re-issued. **There is a clock on this.**
3. **Rotate/revoke endpoints don't exist on the proxy.** Marzneshin returns a *stable* subscription URL (create-or-extend). Consequences: key rotation/reissue can't truly replace a key; block/refund don't cut off the VPN (old key keeps working). Needs new proxy endpoints `rotate-key` + `revoke`.

### Site ↔ backend contract (what the site expects)
- `POST ${MARZNESHIN_PROXY_URL}/external/issue-key`, HMAC header `X-PRSLOY-Signature` (HMAC-SHA256 of body, secret `MARZNESHIN_PROXY_HMAC_SECRET`). Returns `{ marz_username, subscription_url }`.
- Only `period_days` **30 / 180 / 365** are accepted (custom days 400). Idempotency keyed on `payment_id` (= order id); replay → 409 treated as success.
- Site client: `src/lib/marzneshin-proxy.ts` (thin HTTP client, in the SITE repo — nothing to run on a server).

### Recovery path (fastest → full)
1. **Pay the hosting bill today.** Ask the provider how long the suspended VM/disk is kept before deletion — that's the hard deadline.
2. The MOMENT the box is back, **pull a backup off it before anything else:** `bash /opt/hellcat-app/ops/scripts/hellcat-backup.sh` → one AES256 `hellcat-*.tgz.gpg` in `/var/backups/hellcat/`; `scp` it to the founder + off-site (Backblaze B2 per runbook), and grab `/root/.backup-pass` (needed to decrypt). This ends the hostage situation permanently.
3. Verify one test issuance works, then the site's key issuance is live again.
4. If the partner won't restore access: with the backup tarball, stand up the founder's own box from `docs/RECOVERY_RUNBOOK.md` and repoint the site env (`MARZNESHIN_PROXY_URL`, `MARZNESHIN_PROXY_HMAC_SECRET`) to it. Without the tarball → fresh stack, existing keys orphaned.

### Longer-term backend context
See `project_backend_pivot_solo_2026_06_25` (memory): ~100 users now → ~300 max/month; bridges deferred (single-hop to a foreign exit, shared Reality cover); the wedge = clean, long-lived exit IPs (founder's Google-AI-Studio litmus); intermittent 3-4d-up/~24h-down/self-heal outage not yet root-caused.
